# 機能ロードマップ(他の機能候補)

状態: 設計(未実装)。前提は常駐 Bot 化(`resident-bot.md`)。スケジュール管理は `schedule.md`。
価値・コストは個人サーバー(利用者1人)での主観的な見積り。外部サービスの仕様・料金は「要確認」。

## 1. 候補一覧

評価: 価値(高/中/低)、実装コスト(S=1〜2日 / M=3〜5日 / L=1週間超。いずれも Bot 基盤完成後の目安)。

| ID | 機能 | 概要 | 価値 | コスト | 依存 | 備考・リスク |
|---|---|---|---|---|---|---|
| **K01** | **スケジュール管理** | 予定/TODO/リマインド/ダイジェスト | 高 | L | 常駐 Bot、SQLite | 本命。`schedule.md` |
| K02 | ニュース: 日跨ぎ重複防止 | 前日までに載せた記事を除外(F01) | 中 | S | SQLite(`seen_articles`)。Bot 化後は DB で容易 | 現状は Actions で状態を持てず断念。Bot 化の恩恵が大きい |
| K03 | ニュース: キーワード通知 | 指定語を含む記事が出たら随時通知 | 中 | M | 定期フェッチ(30〜60 分)、K02 の既読管理、SQLite | 取得頻度増による相手サイトへの負荷配慮(要確認: 各フィードの利用規約) |
| K04 | ニュース: ジャンル追加・設定 | `/news genre`、ソース/比率の Discord 上での変更 | 中 | M | settings テーブル | 設定を DB に持つ必要。`core/sources.py` の動的化 |
| K05 | 天気 | 朝のダイジェストに天気/降水確率、雨予報の通知 | 中 | S〜M | 天気 API(気象庁の非公式 JSON か Open-Meteo 等。利用条件は要確認)、K01 のダイジェスト | 外部 API 依存。位置情報は設定で固定 |
| K06 | RSS 購読(任意フィード) | `/rss add URL` で購読、新着通知 | 中 | M | `core/fetcher` 流用、SQLite、K02 | K03 と統合可能(購読+キーワード) |
| K07 | GitHub 通知 | リポジトリの Issue/PR/Release/CI 失敗の通知 | 中 | M | GitHub API または RSS(Atom)フィード、トークン(Secrets 増) | 読み取り専用の細粒度トークン。RSS で済むなら K06 に吸収 |
| K08 | メモ | `/memo add/search`、タグ | 中 | S | SQLite | 個人情報の保管(バックアップ対象)。K09 と統合可 |
| K09 | 買い物リスト | `/buy add/list/done`、ボタンで消込み | 中 | S | SQLite、ボタン View(K01 と共通部品) | スマホから素早く使える。K01 の TODO と近いため `todos` に `list` 属性で統合する案 |
| K10 | 習慣トラッカー | 毎日の習慣をボタンでチェック、連続日数、週次サマリー | 中 | M | SQLite、K01 のリマインドと永続 View | リマインド基盤を流用。グラフは任意(画像生成は後回し) |
| K11 | 家計簿 | `/spend 800 ランチ`、月次集計 | 中 | M〜L | SQLite、カテゴリ設計 | 金額データの機微性。CSV エクスポート必須。入力の継続性が課題(自然言語入力が効く) |
| K12 | 自然言語クイック入力の汎用化 | `/ask` でメモ/TODO/買い物/家計簿へ振り分け | 中 | M | K01 の NLP 基盤、各機能 | 振り分けの誤りに注意(必ず確認ボタン) |
| K13 | 週次/月次レビュー | 完了 TODO・習慣・支出の要約を Claude で文章化 | 低〜中 | S〜M | K01, K10, K11 | 個人データを LLM へ送る点の合意が必要 |
| K14 | 外部カレンダー iCal 取り込み | `schedule.md` 第7章 | 中 | M | K01 | ユーザー判断 U2 |
| K15 | タイマー/ポモドーロ | `/timer 25m` | 低 | S | K01 のディスパッチ | 予定の `reminder` で代替可能 |
| K16 | 音声/画像入力(レシート OCR 等) | - | 低 | L | Vision API 等 | 現時点では見送り |

## 2. 優先順位

判断軸: (価値 × 利用頻度) ÷ コスト、既存基盤の再利用度、データ層の共有(SQLite・ボタン View・リマインド基盤)。

| 優先 | 機能 | 理由 |
|---|---|---|
| P0 | 常駐 Bot 化(基盤) | すべての前提。`/news` の再利用で壊さず移行 |
| P1 | K01 スケジュール管理(基本→繰り返し/リマインド→自然言語) | ユーザーの主要要望。基盤(DB・スケジューラ・永続 View)が他機能の土台になる |
| P2 | K02 日跨ぎ重複防止 | DB ができれば低コストで体験が上がる既知の課題(README に記載の制約) |
| P2 | K09 買い物リスト+K08 メモ | 低コスト。K01 の部品(ボタン・DB)の転用で作れる |
| P3 | K05 天気 | ダイジェストに 1 ブロック追加するだけで価値が高い。外部 API 選定のみ要確認 |
| P3 | K10 習慣トラッカー | リマインド基盤の自然な応用。継続して使うかを K01 の利用状況で判断 |
| P4 | K03/K06/K07 通知系(キーワード・RSS・GitHub) | 共通の「定期フェッチ+既読管理」基盤を作ってまとめて実装すると安い |
| P4 | K04 ジャンル/ソースの動的設定 | 設定頻度が低ければ `sources.py` 編集で足りる |
| P5 | K11 家計簿 | 価値はあるが入力の継続・機微データ・集計設計で重い。K12 の自然言語入力ができてから |
| 後回し | K13, K15, K16 | 価値が小さい/代替あり |

## 3. 推奨実装順

1. 常駐 Bot 化の最小構成(`/news`、許可ユーザー検証、Docker、監視)
2. K01 基本(DB、予定/TODO CRUD、`/today` `/week`、ダイジェスト)
3. K01 繰り返し・リマインド・ボタン・取りこぼし再送
4. K02 日跨ぎ重複防止(`seen_articles`。スケジュール用 DB を共用)
5. K01 自然言語(`/ask`)
6. K09 買い物リスト / K08 メモ
7. K05 天気(ダイジェスト拡張)
8. K10 習慣トラッカー
9. 共通「定期フェッチ+既読管理」基盤 → K03/K06/K07
10. K11 家計簿(+ K12 汎用自然言語入力)
11. K14 iCal 取り込み(ユーザーが必要と判断した時点で、位置は前後可)

各ステップの終わりに 1〜2 週間の実運用観察を挟み、使われていない機能は次に進まず削る(個人用なので「使わない機能は作らない」を優先)。

## 4. スケジュール管理との連携ポイント

| 連携先 | 連携内容 |
|---|---|
| 朝のダイジェスト | 天気(K05)、習慣の未達(K10)、買い物リストの件数(K09)、期限が近い TODO を 1 メッセージに集約(ブロックを追加できる設計: `DigestSection` Protocol) |
| リマインド基盤 | 習慣(K10)、定期的な家計入力、ポモドーロ(K15)は `events`/`notifications` を再利用(種別 `kind` を拡張) |
| 通知ボタン | 完了/スヌーズの永続 View を共通部品化(買い物の消込み、習慣のチェックでも使う) |
| TODO | 買い物リスト(K09)は `todos` に `list_name` を持たせて統合する案。メモ(K08)は TODO から「メモに変換」できる |
| 自然言語 | `/ask`(K01)の抽出スキーマを `kind` で拡張(todo/memo/buy/expense) |
| ニュース | K03 のキーワード通知とダイジェストの重複防止、`job_runs` の共有 |
| 外部カレンダー | K14 取り込み予定を `/today` `/week` に混在表示 |
| データ共通 | 単一の SQLite、`owner_id`、`settings`、バックアップ/エクスポートを全機能で共有 |
